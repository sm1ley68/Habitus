## Шаг 2: Связность и доля оценок

Первый запрос брифа (`SELECT city, system, ...`) падает: `city` есть и у
`metro_line`, и у `metro_station` — `ERROR: column reference "city" is
ambiguous`. Ниже — тот же запрос с квалификатором `ml.city`, реальный
результат брифа не менялся, поменялась только формулировка SQL.

```sql
SELECT ml.city, ml.system, count(DISTINCT ml.id) AS lines, count(s.id) AS stations
FROM metro_line ml LEFT JOIN metro_station s ON s.line_id = ml.id
GROUP BY ml.city, ml.system ORDER BY ml.city, ml.system;
```

| city | system | lines | stations |
|------|--------|-------|----------|
| msk  | mcd    | 5     | 94       |
| msk  | mck    | 1     | 31       |
| msk  | subway | 16    | 277      |
| spb  | subway | 6     | 73       |

Числа `lines` здесь — количество **различимых линий после upsert**
(`ON CONFLICT (city, system, ref)`), меньше, чем `lines` в статистике шага 1:
там считались сырые relation-ы Overpass **по направлению** (прямое +
обратное на одну и ту же линию — два upsert в одну строку). Оба числа
верны, просто про разное: 32 сырых relation → 16 линий метро, 30 → 5
диаметров, 12 → 6 линий питерского метро, 2 → 1 МЦК.

Доля оценок по перегонам и пересадкам:

```sql
SELECT city, count(*) FILTER (WHERE estimated) AS estimated, count(*) AS total
FROM metro_edge GROUP BY city;

SELECT city, count(*) FILTER (WHERE outdoor) AS outdoor, count(*) AS total
FROM metro_transfer GROUP BY city;
```

| city | edges estimated | edges total | доля |
|------|-----------------:|------------:|-----:|
| msk  | 764 | 766 | 99.7% |
| spb  | 134 | 134 | 100%  |

| city | transfers outdoor | transfers total |
|------|-------------------:|-----------------:|
| msk  | 2   | 206 |
| spb  | 0   | 0   |

Такая высокая доля `estimated` у перегонов ожидаема и не связана с
`--no-ors`: она про наполнение курируемых файлов (Задача 4), не про пешие
плечи. `data/metro/msk.json` содержит **1 курируемый перегон и 2 курируемые
пересадки** из 766/206 — почти всё выведено по расстоянию, ровно как
описано в брифе Задачи 4 («пустые `edges` — рабочее стартовое состояние»).
`data/metro/spb.json` — 0 курируемых перегонов и пересадок, отсюда 100%.
У Петербурга `metro_transfer` вообще пуст (0 строк) — детектор пересечений
линий не нашёл общих узлов между 6 линиями питерского метро в этом прогоне.

## R37 — кольцо на живых данных

Проверены все три кольцевые линии Москвы: МЦК (`system=mck, ref=14`),
Кольцевая линия метро (`ref=5`) и Большая кольцевая линия (`ref=11`,
БКЛ — физически тоже кольцо, брифом явно не названа, но детектор её тоже
корректно поймал).

Для каждой — станция с `order_index=0` и станция с `order_index=max`:

| линия | станция 0 | станция max | замыкающее ребро (оба направления) | seconds | estimated |
|-------|-----------|-------------|-------------------------------------|--------:|-----------|
| МЦК (id 37)   | Нижегородская (596) | Андроновка (626)      | есть | 170 | true |
| Кольцевая (id 5) | Белорусская (195) | Новослободская (206) | есть | 141 | true |
| БКЛ (id 33)   | Сокольники (514)    | Электрозаводская (542) | есть | 192 | true |

Флаг `ring` истинен для всех трёх на живых данных — замыкающее ребро
существует для каждой. Дальше проверено, что маршрутизатор реально едет
по короткой стороне шва, а не в обход всей линии: вызван
`MetroGraph.route()` из `habitus/online/metro_route.py` напрямую (граф
загружен из БД через `load_graph(conn, "msk")`) для пары «станция 0 →
станция max» на каждой линии.

Результат (`uv run python` со скриптом, использующим `load_graph`/`route`):

```
=== МЦК (ref=14): Нижегородская(596) -> Андроновка(626) ===
ride_seconds=470 trivial=False entry=596 exit=626 estimated=True
  segment: Нижегородская -> Андроновка stops=1 seconds=170 estimated=True

=== Кольцевая (ref=5): Белорусская(195) -> Новослободская(206) ===
ride_seconds=261 trivial=False entry=195 exit=206 estimated=True
  segment: Белорусская -> Новослободская stops=1 seconds=141 estimated=True

=== БКЛ (ref=11): Сокольники(514) -> Электрозаводская(542) ===
ride_seconds=312 trivial=False entry=514 exit=542 estimated=True
  segment: Сокольники -> Электрозаводская stops=1 seconds=192 estimated=True
```

Во всех трёх случаях Дейкстра выбирает **1 перегон через замыкающее
ребро**, а не 28–30 остановок в обход линии — `ride_seconds` совпадает с
временем самого замыкающего ребра плюс интервал посадки (headway), сегмент
`stops=1`. **Вердикт R37: на живых данных подтверждается — детектор кольца
срабатывает верно (в том числе на не упомянутой в R37 БКЛ), замыкающее
ребро существует, маршрут через шов едет коротким путём.** Флаг `false`,
которого опасался бриф, на реальных данных не воспроизведён.

## Шаг 3: Метрики поиска

`OPENROUTER_API_KEY` не задан в `.env` → `llm=None` в `habitus eval`. Это
влияет только на `parse_accuracy` (сверка результата NLU-парсинга запроса с
эталонным `expected_parse` — без LLM `parse_query()` не вызывается вовсе, и
`parse-accuracy` в отчёте `--check`-независимого прогона не считается по
NLU). **Метрики retrieval (precision@10/NDCG@10 варианта `rrf+rerank+prox`,
на которых стоит гейт) от LLM не зависят вовсе** — `ParsedQuery` в
`run_eval()` строится напрямую из `expected_parse` золотого набора
(`habitus/eval/runner.py:94-96`), а реранкер (`habitus/online/rerank.py`) —
локальная BGE cross-encoder модель, не LLM. Ниже — реальные измеренные
retrieval-метрики; `parse_accuracy` из первого прогона (0.97) — артефакт
того, что цикл всё равно не дошёл до LLM-ветки (`llm is not None`), это
значение **не считать измерением NLU** — по факту это `_avg([])` от пустого
списка (см. код), фактически неопределённое/тривиальное число, не
реальная точность парсинга. Точность NLU-парсинга в этом прогоне **не
измерена** — нужен `OPENROUTER_API_KEY`.
