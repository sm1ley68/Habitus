# Разведка тегов метро/МЦК/МЦД в OSM (2026-08-29)

Цель: выяснить, какими тегами в OpenStreetMap реально размечены линии метро,
МЦК и МЦД Москвы, чтобы задать надёжный Overpass-фильтр `TRANSIT_RELATION_FILTER`
(Задача 2/3), не полагаясь на память о разметке — она у диаметров менялась.

Источник: публичный Overpass API (`https://overpass-api.de/api/interpreter`).
Bbox для всех запросов: `(55.00,36.60,56.30,38.60)` — Москва и область.

Overpass регулярно отвечал `runtime error ... timeout. The server is probably
too busy` (HTML-страница вместо JSON) на первую попытку почти каждого запроса.
Все такие случаи ниже помечены явно; после паузы 8–25 секунд повтор всегда
проходил. Между разными запросами выдерживалась пауза не меньше 5 секунд.

## Шаг 1: метро Москвы (`route=subway`)

Команда:

```bash
curl -s -X POST https://overpass-api.de/api/interpreter \
  -H 'User-Agent: Habitus/1.0 (real-estate research)' \
  --data-urlencode 'data=[out:json][timeout:180];relation["route"="subway"](55.00,36.60,56.30,38.60);out tags;' \
  -o /tmp/overpass_subway_msk_tags.json
```

(Сырой ответ этого запроса не коммитится — он не используется ни одним тестом
и не является фикстурой; см. правку по итогам ревью в конце документа. Все
факты из него перенесены в текст протокола ниже.)

Первая попытка: `timeout` (сервер занят). Повтор через 8 с — успех.

Результат: **32 элемента** (по два `relation` на каждую линию — по одному на
каждое направление). Примеры (`id | ref | name | colour`):

## Шаг 2: поиск разметки МЦК и МЦД

### Гипотеза 1 — `route=light_rail` (МЦК)

```bash
curl ... --data-urlencode 'data=[out:json][timeout:180];relation["route"="light_rail"](55.00,36.60,56.30,38.60);out tags;'
```

Результат: **0 элементов**. МЦК как `light_rail` в этом bbox не размечено —
тупик.

### Гипотеза 2 — `route=train`, `ref~"^D[1-5]$"` (МЦД)

```bash
curl ... --data-urlencode 'data=[out:json][timeout:180];relation["route"="train"]["ref"~"^D[1-5]$"](55.00,36.60,56.30,38.60);out tags;'
```

Первая попытка: `timeout`. Повтор через 15 с — успех.

Результат: **28 элементов**. Примеры:

```
10309185  D1  МЦД-1 «Белорусско-Савёловский диаметр»: Лобня => Одинцово      МЦД  #ED9F2D
10309306  D2  МЦД-2 «Курско-Рижский диаметр»: Нахабино => Подольск           МЦД  #DF477C
16213700  D3  МЦД-3 «Ленинградско-Казанский диаметр»: Ипподром => Крюково    МЦД  #E15D29
16272077  D4  МЦД-4 «Калужско-Нижегородский диаметр»: Ж/д => Апрелевка       МЦД  #3FB485
```

Работает, но **пропускает 2 релейшена ветки D4А** (`ref="D4А"` — с русской
буквой «А» на конце, не попадает под `^D[1-5]$`). Это обнаружилось сравнением
с гипотезой 4 (см. ниже).

### Гипотеза 3 — `route=train`, `name~"МЦД"`

```bash
curl ... --data-urlencode 'data=[out:json][timeout:180];relation["route"="train"]["name"~"МЦД"](55.00,36.60,56.30,38.60);out tags;'
```

Результат: **30 элементов** — те же 28 плюс 2 релейшена `ref="D4А"`
(`id=16275211/16275212`, "МЦД-4А «Калужско-Нижегородский диаметр»:
Новопеределкино => Солнечная"). Полнее гипотезы 2, но зависит от того, что
слово «МЦД» всегда есть в `name` — менее устойчиво к будущим переименованиям.

### Гипотеза 4 — `route=train`, `network~"МЦД|MCD"`

```bash
curl ... --data-urlencode 'data=[out:json][timeout:180];relation["route"="train"]["network"~"МЦД|MCD"](55.00,36.60,56.30,38.60);out tags;'
```

Результат: **30 элементов** — тот же набор, что и гипотеза 3 (включая D4А).
`network` — категориальный тег, значение `МЦД` у всех 30 релейшенов, без
исключений. Уникальные `ref`: `D1, D2, D3, D4, D4А`. **У всех 30 релейшенов
есть `colour` в hex-формате**, пропусков нет.

**Вывод по МЦД:** гипотезы 3 и 4 эквивалентны по полноте и превосходят
гипотезу 2 (та теряет ветку D4А из-за буквенного суффикса в `ref`).
Предпочтение — гипотезе 4 (`network`), т.к. это структурный категориальный тег,
а не текст в `name`, который переписывается чаще.

### Гипотеза 5 — `route=train`, `name~"МЦК"` (МЦК, попытка через train)

curl ... --data-urlencode 'data=[out:json][timeout:180];relation["route"="train"]["name"~"МЦК|Центральная кольцевая|Московское центральное кольцо"](55.00,36.60,56.30,38.60);out tags;'

Первая попытка: `timeout`. Повтор через 15 с — успех.

Результат: **0 элементов**. В `name` реальной линии МЦК подстроки «МЦК» нет
(см. ниже — там официальное название без аббревиатуры).

### Гипотеза 6 — любой relation с `name~"МЦК"` (без ограничения по route)

```bash
curl ... --data-urlencode 'data=[out:json][timeout:180];relation["name"~"МЦК|Московское центральное кольцо"](55.00,36.60,56.30,38.60);out tags;'
```

Первая попытка: `timeout`. Повтор через 20 с — успех.

Результат: **103 элемента**, но это все посторонние сущности: автобусные
(`route=bus`) и трамвайные (`route=tram`) маршруты, названные по станциям МЦК
(«Автобус м23: МЦК «Панфиловская» => …»), и релейшены
`public_transport=stop_area` для станций МЦК (`МЦК Лужники`, `МЦК Белокаменная`
и т.д. — подтверждают, что станции МЦК в OSM существуют, но сам маршрут
`route=train` среди них не нашёлся).

### Гипотеза 7 (найдена) — `route=train`, `ref="14"`

По аналогии с официальным статусом МЦК как «14-й линии» Московского метро:

```bash
curl ... --data-urlencode 'data=[out:json][timeout:180];relation["route"="train"]["ref"="14"](55.00,36.60,56.30,38.60);out tags;'
```

Результат: **2 элемента** — именно МЦК:

```json
{
  "id": 6548266,
  "tags": {
    "colour": "red",
    "colour:infill": "white",
    "int_name": "MCC ⥀",
    "name": "Московское Центральное Кольцо (против часовой)",
    "network": "Московский метрополитен",
    "operator": "ОАО «РЖД»",
    "ref": "14",
    "route": "train",
    "service": "commuter",
    "short_name": "МЦК(против часовой)"
  }
}
```

Второй элемент (`id=6548267`) — то же самое по часовой стрелке.

**Важные находки:**
- `network` у МЦК — `"Московский метрополитен"`, **та же строка**, что и у
  обычного метро (`route=subway`). Различать метро и МЦК по `network`
  бессмысленно — различитель именно `route` (`subway` vs `train`) + `ref="14"`.
- `colour` у МЦК — **`"red"`, словесное имя CSS-цвета, не hex** (в отличие от
  всех линий метро и МЦД, где `colour` всегда `#RRGGBB`). Это единственное
  расхождение формата во всей разведке — **фронтовый фолбэк палитры обязан
  уметь либо резолвить именованные CSS-цвета, либо игнорировать `colour` для
  МЦК и подставлять собственный брендовый цвет** (официальный маруновый МЦК
  `#B2003B`/похожий, но из тегов OSM этот hex не получить).
- `int_name` содержит `"MCC ⥀"` / `"MCC ⥁"` — тоже годный, но менее строгий
  признак (нужна отдельная нормализация от юникод-стрелок).

### Гипотеза 8 (проверка на ложные срабатывания) — `route=train`, `network="Московский метрополитен"`

```bash
curl ... --data-urlencode 'data=[out:json][timeout:180];relation["route"="train"]["network"="Московский метрополитен"](55.00,36.60,56.30,38.60);out tags;'
```

Первая попытка: `timeout`, вторая тоже `timeout`, третья (после ~25 с) —
успех. Результат: **2 элемента** — те же самые `id=6548266/6548267`. Это
подтверждает, что в данном bbox под `route=train` + `network="Московский
метрополитен"` не попадает ничего постороннего: фильтр `ref="14"` не даёт
ложноположительных совпадений и не является случайным совпадением с чем-то
ещё.

## Шаг 3: полная фикстура с members (одна линия метро)

Изначальная команда из брифа:

```bash
curl ... --data-urlencode 'data=[out:json][timeout:180];relation["route"="subway"]["ref"="1"](55.00,36.60,56.30,38.60);out body geom;' \
  -o tests/fixtures/overpass_subway_msk.json
```

**Отклонение от брифа (важно для Задачи 3):** `out body geom;` без
рекурсивного дозапроса (`>;`) отдаёт для `relation`-выборки только сами
релейшены, где у `node`-members есть `lat/lon`, а у `way`-members — инлайновая
`geometry`, **но у node-members нет `tags`** — то есть нет `name` станции.
Это не даёт выполнить требование «у станций есть `name` и координаты».
Использован скорректированный запрос с рекурсией:

```bash
curl -s -X POST https://overpass-api.de/api/interpreter \
  -H 'User-Agent: Habitus/1.0 (real-estate research)' \
  --data-urlencode 'data=[out:json][timeout:180];relation["route"="subway"]["ref"="1"](55.00,36.60,56.30,38.60);out body;>;out body geom;' \
  -o tests/fixtures/overpass_subway_msk.json
```

Результат: **1173 элемента** — 2 `relation` (оба направления Сокольнической
линии, `ref="1"`), 1059 `node` (станции/платформы с `tags.name` + вершины
геометрии путей без тегов), 112 `way` (сегменты пути с инлайновой
`geometry`). Роли members: `stop`, `stop_entry_only`, `stop_exit_only`,
`platform`, `platform_entry_only`, `platform_exit_only`, пустая роль у
вспомогательных ways.

## Шаг 4: ужатие фикстуры

Скрипт из брифа рассчитан на плоский список `node`/`way` без «мусорных»
геометрических узлов — в текущей структуре (после рекурсивного дозапроса) он
оставил бы все 1059 нод без разбора. Ужатие адаптировано под реальную форму
данных: оставлен **один** `relation` (первое найденное направление,
`id=305810`, `ref=1`) и **все** `node`-members этого релейшена (это станции и
платформы с именами — 27 штук, вершины трассы среди них не встречаются, они
живут только внутри `way.geometry`).

**Правка по итогам ревью (way для геометрии отбирались неверно).** Первая
версия скрипта брала «первые 3 `way` по порядку в топ-уровневом списке
элементов» без учёта их роли в `relation.members`. У линии метро в members
одновременно есть way с ролью `platform`/`platform_entry_only`/
`platform_exit_only` (контуры платформ, 14 штук) и way с **пустой ролью**
(48 штук — это и есть сегменты трассы). Наивная нарезка `[:3]` по факту взяла
три way с ролью `platform`/`platform_entry_only`/`platform_exit_only`, а не
трассу. Парсер Задачи 3 читает геометрию только из
`m.get("type") == "way" and not m.get("role")` — то есть из way с пустой
ролью; в первой версии фикстуры таких в отобранной тройке не было ни одного,
и `parse_route_relations` возвращал бы `geometry == []`.

Исправлено: way для фикстуры отбираются **по роли `''` (пустая) в
`relation.members`**, первые 3 таких way (из 48 доступных) — это и есть
сегменты трассы Сокольнической линии.

Итоговый файл `tests/fixtures/overpass_subway_msk.json`:
- 1 `relation` (Сокольническая линия, направление Бульвар Рокоссовского →
  Потапово), 27 `node` (все с `tags.name` и `lat`/`lon`), 3 `way` с пустой
  ролью в members (все с `geometry` — списком `{lat, lon}`).
- Роли node-members: `stop` (25 штук), `stop_entry_only` (1), `stop_exit_only`
  (1). Роль way-members в фикстуре — пустая строка у всех трёх (осознанно:
  это единственная роль, которую парсер Задачи 3 читает как трассу).
- Размер: **~16.3 КБ**.

**Число станций, которое реально извлекает парсер Задачи 3, — 25, а не 27.**
Парсер фильтрует node-members строго по роли `stop` или `platform`
(`_STOP_ROLES = ("stop", "platform")`); роли `stop_entry_only` и
`stop_exit_only` под это правило не попадают и станциями не становятся. В
фикстуре сохранены все 27 node-members (буквально по инструкции брифа — «все
node-members»), но на выходе `parse_route_relations` окажется ровно 25
`StationRaw`.

Проверено не глазами, а прогоном **дословной копии** `parse_route_relations`
из `task-3-brief.md` (Step 3) поверх итоговой фикстуры — воспроизводит все
пять тестов из `task-3-brief.md` (Step 1) вручную, без создания самого файла
`tests/test_metro_parse.py` (это по-прежнему задача Задачи 3):

- `test_parses_line_identity` — OK, `ref='1'`, `colour='#E42313'`.
- `test_stations_keep_relation_order` — OK, **станций извлечено: 25**
  (без дублей, все с именем и координатами в допустимом диапазоне).
- `test_geometry_is_lng_lat_pairs` — OK, **точек геометрии извлечено: 70**
  (из 3 way с пустой ролью), первая точка `[37.7342937, 55.8146309]` —
  порядок `[lng, lat]` подтверждён (долгота ~37, широта ~55 — не перепутаны).
- `test_relation_without_stops_is_skipped` — OK (синтетический payload, от
  фикстуры не зависит).
- `test_systems_cover_all_three` / `test_name_normalization` — не зависят от
  этой фикстуры, не перепроверялись здесь.

## Вывод — три строки Overpass-фильтра для `TRANSIT_RELATION_FILTER`

Готовы к копированию в `habitus/geo/metro.py` (Задача 2/3):

```python
"subway": 'relation["route"="subway"]',
"mck":    'relation["route"="train"]["ref"="14"]',
"mcd":    'relation["route"="train"]["network"~"МЦД|MCD"]',
```

Уверенность по каждой строке:

- **`subway`** — высокая. 32/32 релейшена с непустым `ref` и hex `colour`,
  проверено напрямую, стабильная и давно устоявшаяся разметка.
- **`mcd`** — высокая. 30/30 релейшенов, все с `network="МЦД"` и hex `colour`,
  включая нестандартную ветку `D4А`, которую теряет более узкий вариант по
  `ref~"^D[1-5]$"`. Единственный риск — если когда-нибудь появится
  `network="MCD"` (латиницей) без кириллического варианта: фильтр это уже
  учитывает через `|MCD`.
- **`mck`** — средняя. Всего 2 релейшена, оба найдены и перепроверены двумя
  независимыми гипотезами (`ref="14"` и `network="Московский метрополитен"` с
  `route="train"`), ложных срабатываний нет. Риск: `ref="14"` — это
  единственный присвоенный на сегодня номер линии МЦК; если разметчики его
  когда-то поменяют (маловероятно, это официальный номер линии Мосметро), фильтр
  перестанет находить МЦК. Более смысловая альтернатива
  `["route"="train"]["network"="Московский метрополитен"]` даёт тот же
  результат в этом bbox, но менее специфична (в другом городе/bbox под тот же
  `network` теоретически может попасть что-то ещё) — оставлена в протоколе
  как запасной вариант, а не как рекомендуемая строка.

## Фолбэк палитры (для фронта)

- Метро (32 линии) и МЦД (5 линий/веток) — `colour` всегда `#RRGGBB`,
  спецобработка не нужна.
- **МЦК — `colour="red"` (словесное имя CSS-цвета, не hex).** Фронтовый код
  палитры должен либо резолвить именованные CSS-цвета, либо — надёжнее —
  считать МЦК отдельным случаем и не полагаться на `colour` из OSM вовсе,
  задав официальный маруновый цвет МЦК константой в коде.
