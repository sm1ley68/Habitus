# Базовая линия eval после расширения golden-set c-серией

Прогон 22 августа 2026 на восстановленной базе. Команда:

```
uv run python -m habitus.eval.curate && uv run habitus eval
```

БД: **6370 активных объявлений** с эмбеддингами, порт 5544. Конфигурация по
умолчанию — `rerank_pool_n=40`, `rerank_max_length=256`, `rerank_top_n=10`,
`result_max_n=30`.

## Что изменилось в наборе

Golden-set вырос с 16 до 22 запросов. Добавлена **c-серия** (`c01`–`c06`) —
запросы, которые **не решаются** SQL-фильтрами и proximity: район или улица в
адресе, станция метро по названию. Эталон для них строится правилами
курирования через поле `match` (`address_ilike` / `metro_ilike`,
параметризованно), поэтому он воспроизводим, а не размечен вручную.

Оси, для которых правила построить не из чего, в набор **не вошли**: тип дома
(колонки нет в БД) и чистый вайб из описания. Честнее не иметь запроса, чем
иметь фиктивный эталон.

## Почему гейт судит по precision, а не по recall

У запроса без ранжирующего сигнала (`curate.score()` не различает объекты —
нет `geo` и `noise_max`) релевантен **весь пул**, а он бывает в сотни объектов:
у b02 «однушка до 25 млн» — 1067, у c02 «Павелецкая» — 231. `recall@10` у таких
запросов упирается в потолок `10/|пул|` ≈ 0.01 и меряет размер базы, а не
качество поиска.

`precision@10` — «сколько из показанных десяти действительно удовлетворяют
запросу» — от размера пула не зависит. По ней и гейт; recall остаётся в отчёте,
но сопоставим только внутри серии.

## По сериям (`rrf+rerank+prox`)

| серия | что меряет | recall@10 | precision@10 | NDCG@10 | MRR | n |
|---|---|---|---|---|---|---|
| a | структурные фильтры + proximity, узкие пулы (эталон = топ-10) | 0.25 | 0.25 | 0.26 | 0.40 | 10 |

## Что видно

- **Текстовая c-серия — лучшая по precision (0.73).** Семь из десяти
  показанных объектов действительно у запрошенного метро или в запрошенном
  районе, хотя `build_where` эту ось не фильтрует вовсе: работает связка
  dense + sparse + реранк по `doc_text`. Это и была цель расширения набора —
  раньше стадия не измерялась.
- **b-серия не «худшая», как казалось по recall.** Её recall 0.03 — прямое
  следствие пула в сотни объектов, а precision 0.53 и MRR 0.62 показывают
  нормальную работу. Именно этот случай и подтолкнул перевести гейт на
  precision.
- **a-серия: precision = recall = 0.25.** У неё эталон ровно топ-10, поэтому
  метрики совпадают по построению. Самая низкая precision из трёх серий —
  структурные запросы с proximity ранжируются хуже текстовых.
- **Proximity даёт основной прирост, реранк — добавку поверх него.**
  `rrf` → `rrf+prox`: precision 0.37 → 0.42, NDCG 0.36 → 0.45. Добавление
  реранка: 0.42 → 0.45 и 0.45 → 0.46. Реранк **без** proximity качество даже
  слегка снижает (0.37 → 0.34) — он слеп к точным минутам, их добавляет
  proximity-стадия.
- **MRR 0.58** при precision 0.45: первый релевантный объект в среднем на
  второй позиции.

## Пороги гейта

`uv run habitus eval --check` по умолчанию требует:

- `--min-precision 0.40` — измеренное 0.45 минус 0.05;
- `--min-ndcg 0.41` — измеренное 0.46 минус 0.05.

Гейт судит по варианту `rrf+rerank+prox`. Запас 0.05 покрывает шум одного
прогона, а не ожидаемое улучшение: если метрика просядет ниже — это регресс,
а не разброс. Менять пороги только вместе с новым прогоном и новой записью
здесь.

**Перед `--check` всегда перекурируйте эталон** (`python -m habitus.eval.curate`):
golden-set привязан к снимку данных, а сбор идёт четыре раза в сутки. Без этого
красный гейт чаще означает «эталон отстал от базы», чем «поиск сломался».

## Оговорки

- Гейт судит retrieval **без резолва области**: `run_eval` зовёт
  `hybrid_search` напрямую и `pq.area` игнорирует, тогда как `run_search` в
  проде дополнительно резолвит область в гео-предикат и умеет relaxation. Для
  a/b это безразлично, для c01/c03/c05 (`area` заполнен) eval меряет более
  трудную задачу, чем прод.
- Имя файла содержит 18 августа — дату задачи, поставившей гейт. Сам замер
  сделан 22 августа, после восстановления базы.

## История: почему замер переделывался

Первая версия заметки (прогон 20 августа, recall 0.34 на 3291 объекте) отозвана
по двум причинам, обе исправлены:

1. **Дефект курирования.** При вырожденном скоре `curate` резал пул до
   `TOP_N`, объявляя произвольные 10 наименьших `external_id` «лучшими», а
   десятки одинаково подходящих объектов — нерелевантными. Это занижало b- и
   c-серии и делало NDCG измерением случайной перестановки. Теперь такой пул
   релевантен целиком с равной оценкой.
2. **База схлопнулась с 3291 активного объявления до 417.** Причина —
   взаимодействие двух вещей: `MAX_OFFERS` снижен до 400 (щадящий режим), а
   `deactivate_missing` гасил всё, чего нет в текущем снимке. Один щадящий цикл
   погасил всё, что собрали предыдущие. Поставлена защита
   (`SNAPSHOT_COVERAGE_MIN`), база восстановлена из `listings.csv`.

Цифры двух прогонов **несопоставимы построчно**: изменились и база (3291 → 6370),
и правило курирования, и набор метрик.
