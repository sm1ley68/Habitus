# Падения Postgres на длинных прогонах — разбор

## Симптом

На длинных прогонах `uv run habitus eval` (и полного `pytest` параллельно с ним)
рвалось соединение с БД:

```
psycopg.OperationalError: consuming input failed: server closed the connection unexpectedly
```

В логе БД при этом:

```
LOG:  server process (PID N) exited with exit code 2
LOG:  terminating any other active server processes
LOG:  all server processes terminated; reinitializing
```

Дальше — автоматическое WAL-восстановление. Данные каждый раз оставались целы.
Наблюдалось 4 раза; часть прогонов при этом проходила нормально, то есть эффект
плавающий.

## Что означает «exit code 2»

Постмастер различает два случая: `was terminated by signal N` и `exited with exit
code N`. Здесь второе — процесс завершился сам, а не был убит сигналом. Это сразу
исключает OOM-killer (SIGKILL) и segfault (SIGSEGV). Для самого Postgres код 2
нехарактерен: `FATAL` даёт 1, `PANIC` уходит через abort. Код 2 отдаёт обработчик
`quickdie()` — реакция на SIGQUIT, то есть бэкенду прилетал сигнал извне.

## Что проверено и отвергнуто

| Гипотеза | Проверка | Итог |
|---|---|---|
| Мало `/dev/shm` под параллельные воркеры | подняли до 1 ГБ | падение повторилось — не причина |
| OOM внутри виртуалки | `dmesg` ядра VM | записей OOM нет |
| Нехватка памяти самому Postgres | `docker stats` во время прогона | 162 МБ из 6.77 ГБ — давления нет |
| Тяжёлое чтение (HNSW + PostGIS) | 4 мин нагрузки, ~235 тыс. поисков | не воспроизводится |
| Обслуживание HNSW при записи | 50 тыс. вставок, 50 построений индексов | не воспроизводится |

## Причина

Хост — Apple M3 (arm64). Образ БД собирался от `postgis/postgis:16-3.4`, который
публикуется **только под amd64**. При этом в Docker Desktop
`UseVirtualizationFramework = False`, то есть Rosetta не задействована и amd64-код
исполнялся полной программной эмуляцией QEMU. Под ней и происходила случайная
гибель бэкендов на длинных нагрузках.

Косвенное, но сильное подтверждение — цена эмуляции по скорости (одинаковая
нагрузка, 60 с, 3 потока поиска + 2 гео):

| | amd64 под QEMU | нативный arm64 |
|---|---|---|
| векторных циклов | 2 863 | 7 765 |
| гео-проходов | 14 | 264 |

Гео-запросы (PostGIS `ST_DWithin` по geography, 46 тыс. линий слоя шума) шли в
**19 раз** медленнее — отсюда же и одиннадцатиминутный `enrich` до появления
индекса по `(geom::geography)`.

## Что сделано

`Dockerfile.db` переведён с `postgis/postgis:16-3.4` на официальный `postgres:16`
(мультиарх) с установкой PostGIS и pgvector из PGDG — канонического репозитория
обоих. Стороннего издателя образа в цепочке поставки нет, эмуляции тоже.

Данные переносились через `pg_dump -Fc` → пересоздание тома → `pg_restore`, а не
переиспользованием каталога: старый каталог был инициализирован под glibc с
collation 2.31, новый образ даёт 2.36, а при расхождении версии collation
текстовые индексы могут молча терять строки.

После перехода: `pytest` 203 passed, Go-пакеты зелёные, `habitus eval` проходит
целиком (recall@10 0.67 на `rrf+rerank+prox`), падений нет.

**Базовый образ обязан оставаться мультиарх.** Возврат на `postgis/postgis` вернёт
эмуляцию молча — ни одна проверка на это не ругнётся.

## Остаётся на стороне машины

Docker Desktop отдаёт виртуалке `MemoryMiB = 7168` при 8 ГБ физической памяти.
Во время прогона eval на хосте оставалось ~0.1 ГБ свободной памяти и ~12 ГБ свопа:
Postgres из этих 7 ГБ занимает 162 МБ, а модели BGE-M3 и реранкера крутятся на
хосте и упираются в остаток. Это не причина падений (они объяснены эмуляцией), но
причина общей вялости. Разумно снизить лимит виртуалки до 2–3 ГБ — настройка
глобальная, в Docker Desktop → Settings → Resources.
