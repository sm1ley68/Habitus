## Конфигурация стенда

Важное отличие от базового `docker-compose.yml`: **ML-сервис гоняется нативно на
хосте**, а не в контейнере — так задумано локальным `docker-compose.override.yml`
(CPU-реранк в контейнере даёт 1–2.5 минуты на запрос против секунд на MPS).

Порт нативного ML пришлось сменить с 8000 на **8001**: 8000 на этой машине занят
посторонним процессом другого проекта (`bets_server.py`, висит с середины
августа). Именно он отвечал шлюзу `404` на прогреве — отсюда падение
`ML warm-up failed; backend will not accept traffic` при каждом старте.
Диагноз выглядел как «сломан бэкенд», а был занятый порт.

Запуск нативного ML:

```bash
uv run uvicorn habitus.online.service:app --host 127.0.0.1 --port 8001
```

Контейнер `ml-service` при этом гасится: две копии BGE-M3 в памяти на 8 ГБ
машину душат. Compose поднимает его как зависимость шлюза — после старта
`backend` контейнер можно останавливать, шлюз уже ходит на хост.

## Шаг 3 — живой Циан: НЕ ПРОВЕРЕНО

`CIAN_PROXIES` в `.env` пуст. Без прокси запрос ушёл бы на cian.ru прямо с IP
разработчика, и ожидаемым исходом был бы 403 или капча. Проверка не запускалась —
решение о живом трафике за владельцем проекта.

**Что это значит для фичи.** Ветка «объявления нет ни в кабинете, ни в витрине»
(вердикт `new`) на практике не подтверждена ни разу. Жизнеспособность импорта с
Циана — по-прежнему главное непроверенное допущение всей фичи. Деградация до
`cian_unavailable` покрыта юнит-тестами (`TestPreviewMapsCianBlockToUnavailable`,
экран `CianUnavailable` с уходом в ручную форму), но на живом Циане не
наблюдалась.

Чтобы закрыть: прописать рабочие резидентные прокси в `CIAN_PROXIES`, импортировать
ссылку на объявление, которого нет в базе, и записать сюда — с какими прокси, с
какой частотой блокировок, сколько живёт сессия.

## Шаг 4 — сквозной путь ручного объявления

Через шлюз (`POST /api/v1/owner/listings`) создано объявление: Москва,
Кожуховская улица 14, 2 комнаты, 56.5 м², кухня 11 м², 6/14 этаж, 13 400 000 ₽,
координаты `[37.6739, 55.7086]`, окна на юг.

- Создание — `201`, статус `draft`, `external_id` вида `owner_<hex>`,
  координаты вернулись в `[lng, lat]`.
- Публикация — `200`, статус `published`, `published_at` проставлен,
  `import_error` пуст.
- В витрине: `source=owner`, `owner_managed=t`, `is_active=t`, `doc_text` есть,
  `embedding` есть, координаты совпали, `walk_min_metro` заполнен — точечное
  обогащение отработало.
- Поиск: по запросу «двушка со светлой кухней одиннадцать метров» объект в
  выдаче. По запросу «тихая двушка окнами во двор рядом с Кожуховской, до 14 млн»
  его перебили по ранжированию объявления Циана — это поведение выдачи, не дефект
  кабинета.
- Досье строится: `dossier-v1`, три блока (`logistics`, `view_and_climate` —
  secondary, `social_environment` — hero). Блоки честно деградируют там, где
  данных мало. `SynthName` имени не дал.
- Удаление — `204`. Объявление ушло из витрины в `is_active=false`, карточка
  кабинета удалена. Это задуманное поведение: строка витрины остаётся, чтобы
  повторная публикация оживила её вместе с уже посчитанным эмбеддингом.

Тестовые данные (пользователь `acceptance@habitus.local`, строка `owner_…`)
после проверки удалены.

## Побочное: диск и память

Пересборка образов упёрлась в переполненный диск (осталось было 146 МБ из 228 ГБ),
демон Docker от этого завис. Освобождено около 30 ГБ: кэш сборки Docker (26.6 ГБ),
остановленные контейнеры, кэши `go-build`, `npm`, браузера и загрузчиков
обновлений. Тома `habitus_pg` и `habitus_hf` (8.7 ГБ) и `~/.cache/huggingface`
(7.6 ГБ) не тронуты.

Память Docker Desktop оставлена прежней — 3072 МБ. На 8 ГБ машины поднимать её
нельзя: нативный ML занимает около 2.5–3 ГБ, и вдвоём они уводят систему в своп.
Ровно поэтому контейнерный `ml-service` в этой конфигурации должен быть погашен.
