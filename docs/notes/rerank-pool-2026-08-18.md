# Замер: срез пула реранка (`rerank_pool_n`)

Задача: узнать, при каком `rerank_pool_n` качество варианта `rrf+rerank+prox`
ещё не просело более чем на 0.03 recall@10 относительно `pool_n=100`
(«как было» до `prefilter_pool`, введённого в 7ab24c6/03ba656), и зафиксировать
это число как дефолт.

> **Статус: промежуточный.** Цифры ниже сняты на коде между Task 4 и Task 5.
> Task 5 убрала жёсткий фильтр `window_orientation` из `build_where`, то есть
> выдача по запросам с ориентацией изменилась, а Task 9 ещё раз перекурирует
> эталон и добавит c-серию. Финальный замер и выбор дефолта — после Task 9,
> одним сквозным прогоном по итоговому коду. Здесь зафиксирован порядок
> величины, а не окончательное решение.

## Как получены цифры

БД поднята (порт 5544, 3291 объявление с эмбеддингами). Команда на каждую
конфигурацию:

```
RERANK_POOL_N=<N> RERANK_MAX_LENGTH=256 uv run habitus eval
```

Время — весь прогон `uv run habitus eval` (parse-accuracy + 5 retrieval-вариантов
на 16 запросах golden-set), а не изолированная стадия реранка: остальные стадии
(dense, rrf, rrf+prox) одинаковы во всех прогонах, поэтому разница во времени
между строками объясняется стадией `rrf+rerank`/`rrf+rerank+prox`.

## Эталон был перекурирован перед замером

Первая попытка замера дала recall@10 = 0.13 против 0.65 из
`docs/notes/eval-baseline-2026-08-14.md`. Причина оказалась не в `pool_n`:
просели все варианты разом, включая `dense`, который через `prefilter_pool` и
реранк вообще не проходит. Golden-set (`habitus/eval/queries.yaml`) курировался
в `fd3a85c`, а свежий срез объявлений пришёл позже, в `ba9daee` — id из
`relevant_ids` в базе остались, но перестали проходить структурные фильтры или
потеряли ранг.

Поэтому перед замером эталон перекурирован (`python -m habitus.eval.curate`,
шаг из Task 9). Совпадение нового эталона со старым — 1–5 из 10 по a-серии,
b-серия размечена впервые. Все четыре конфигурации ниже прогнаны на **одном и
том же** перекурированном эталоне и одном срезе БД, без повторного курирования
между прогонами — иначе цифры были бы несопоставимы между собой.

## Результаты (`rrf+rerank+prox`, n=14 запросов с `relevant_ids`)

| pool_n | recall@10 | NDCG@10 | MRR | время прогона eval |
|---|---|---|---|---|
| 100 | 0.34 | 0.37 | 0.54 | 2636 c (44 мин) |
| 60  | 0.35 | 0.37 | 0.55 | 1354 c (23 мин) |
| 40  | 0.33 | 0.35 | 0.51 | 1416 c (24 мин) |
| 25  | 0.34 | 0.35 | 0.48 | 626 c (10 мин) |

parse-accuracy: 0.97 (одинакова во всех прогонах, к измеряемой метрике
отношения не имеет — приведена для полноты вывода).

Полные таблицы по вариантам — в `/tmp/eval-pool-<N>.log` на машине прогона;
здесь оставлена только измеряемая строка плюс `rrf+prox` для контроля:
`rrf+prox` даёт 0.24 / 0.27 / 0.52 во **всех** четырёх прогонах, что и
подтверждает, что менялся ровно один параметр.

## Что уже видно

- **Качество плоское по всему диапазону.** Разброс recall@10 — 0.33…0.35 при
  критерии «не более 0.03 просадки». Даже `pool_n=25` укладывается: 0.34 против
  0.34 у сотни. Кросс-энкодер не находит в хвосте пула ничего, чего не нашёл бы
  в голове.
- **Время линейно по `pool_n`,** как и предполагалось (реранк линеен по числу
  пар): 25 → 626 c, 60 → 1354 c, 100 → 2636 c. Выбивается только 40 (1416 c
  против ожидаемых ~1000) — прогон шёл под конкурирующей нагрузкой на CPU
  (параллельно шли Go-тесты и pytest), так что это артефакт замера, а не свойство
  конфигурации. По этой же причине абсолютные секунды здесь — верхняя оценка.
- **MRR слегка деградирует к малым пулам** (0.55 → 0.48 от 60 к 25) при том, что
  recall держится: голова выдачи чуть хуже упорядочена, хотя нужные объекты в
  топ-10 попадают. Это довод против самого агрессивного среза.

Предварительно 60 выглядит лучшей точкой (лучший recall и MRR из всех четырёх,
вдвое быстрее сотни), но фиксировать дефолт до финального прогона рано.
