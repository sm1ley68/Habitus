# Гео-зоны запроса: округа / районы / кольца / разговорные названия

**Дата:** 2026-07-18
**Статус:** дизайн (спека)

## Проблема

Пользователь указывает район словами: «на севере москвы», «в центре», «в Хамовниках»,
«у Патриков», «рядом со Сколково». Текущая реализация (`resolve_area`, коммит c45530f)
режет город грубо: стороны света — bbox ровно по центру (объект у Кремля попадает в
«север»), «центр» не выделен как зона, районы и разговорные названия не поддержаны,
именованные места идут в Nominatim, который разговорные топонимы («Патрики») не знает.

## Цель

Полностью удовлетворять запрос по району: **стороны света + центр, административные
округа и районы, кольцевые зоны, именованные места и разговорные названия**. Совпадение
с ментальной моделью москвича, как на ЦИАН/Яндекс.Недвижимости.

## Решения (утверждены на брейншторминге)

- **Охват:** всё перечисленное выше (максимальный).
- **Пустая зона:** строго + авто-расширение (район→округ→снять) с честной пометкой в
  выдаче, в духе текущей relaxation-петли.
- **Источник геометрии:** реальные полигоны OSM (округа admin_level=5, районы
  admin_level=8), не аппроксимация.
- **«Центр» = ЦАО** (широкий, ~66 км², ~300 наших объектов) по умолчанию; «внутри
  Садового» (строгий, ~19 км²) — отдельная явная зона.
- **НЕ делаем:** H3/geohash, изохроны, обучение моделей (незачем на ~10³ точек — вся
  геоматематика сводится к разовому `ST_Contains` при загрузке).

## Архитектура

Слоёный резолвер поверх предвычисленных зональных колонок. Ключевой инсайт: на 979
объявлениях принадлежность зоне считается ОДИН раз при загрузке (`ST_Contains`), поиск
превращается в фильтр по строковой колонке — идеально для LLM-роутера (модель выбирает
имя зоны из закрытого списка).

```
NLU (area: str) → resolve_area(area, conn) → (SQL-предикат, label, widen-chain)
                                              ↓
                          build_where(extra_sql=…) → retrieval + авто-расширение
```

### Данные

**Таблица `admin_zones`** — полигоны из OSM (разовый импорт):
```sql
CREATE TABLE admin_zones (
    id       bigserial PRIMARY KEY,
    kind     text NOT NULL,           -- 'okrug' | 'raion' | 'ring'
    name     text NOT NULL,           -- 'ЦАО' | 'Хамовники' | 'Садовое кольцо'
    aliases  text[] NOT NULL DEFAULT '{}',
    geom     geometry(MultiPolygon, 4326) NOT NULL,
    updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX admin_zones_geom_gix ON admin_zones USING GIST (geom);
CREATE UNIQUE INDEX admin_zones_kind_name ON admin_zones (kind, lower(name));
```

**Таблица `named_zones`** — курируемый словарь разговорных/брендовых зон (~20-30),
которых нет в админ-делении и не знает геокодер:
```sql
CREATE TABLE named_zones (
    id       bigserial PRIMARY KEY,
    name     text NOT NULL,           -- 'Патриаршие пруды'
    aliases  text[] NOT NULL DEFAULT '{}',  -- {'Патрики','Патриаршие'}
    lon      double precision NOT NULL,     -- якорь
    lat      double precision NOT NULL,
    radius_m double precision NOT NULL DEFAULT 700
);
```
Наполняется из закоммиченного сида (`data/named_zones.seed.json` или SQL). Примеры:
Патрики→Патриаршие пруды, Золотая миля→Остоженка, Сити→ММДЦ, Чистые пруды, Тверская.

**Колонки в `listings`** (предвычисление при загрузке):
```sql
ALTER TABLE listings ADD COLUMN okrug text;   -- 'ЦАО', 'САО', …
ALTER TABLE listings ADD COLUMN raion text;   -- 'Хамовники', …
CREATE INDEX listings_okrug_ix ON listings (okrug);
CREATE INDEX listings_raion_ix ON listings (raion);
```
Кольцевая принадлежность (внутри Садового) считается на запросе через `ST_Within`
против `admin_zones` kind='ring' — редкий запрос, предвычисление не нужно.

### Импорт зон — CLI `import-zones`

Аналог `import-evidence`/`import-osm-features`:
```
uv run habitus import-zones --geojson data/moscow_admin.geojson
```
- Вход — `FeatureCollection` полигонов округов (admin_level=5) и районов
  (admin_level=8), полученный из OSM (osm-boundaries.com экспорт или build-скрипт через
  Overpass + сборка полигонов в PostGIS). Каждый Feature: `properties.kind`
  ('okrug'|'raion'), `properties.name`, геометрия Polygon/MultiPolygon.
- Импорт идемпотентен по `(kind, lower(name))` (как evidence по source_id).
- «Садовое кольцо» (kind='ring') — из OSM-линии кольца (`ST_MakePolygon`) или
  аппроксимация кругом R=2.5км; грузится тем же импортом.
- После загрузки полигонов — **backfill** `listings.okrug`/`raion` через `ST_Contains`
  (мгновенно на 979 точках). Повторный `import-zones` пересчитывает.
- `named_zones` грузятся отдельной подкомандой/сидом (`import-named-zones` или в рамках
  `import-zones` из закоммиченного файла).

### Резолвер `resolve_area(area, conn, *, geocoder) → ZoneMatch | None`

`ZoneMatch = (sql: str, params: tuple, label: str, widen: list[tuple[str,tuple,str]])`
— SQL-предикат для `build_where(extra_sql)`, человекочитаемый label, и цепочка
расширений (каждый шаг — более широкий предикат + пометка).

Цепочка распознавания (по убыванию точности, первое совпадение выигрывает):

1. **Сторона света / центр** (константный map в коде, не таблица):
   - `центр` → `okrug = 'ЦАО'` (широкий). `внутри садового` → `ST_Within(geom, <Садовое>)`.
   - `север`→`okrug = ANY('{САО,СВАО,СЗАО}')`; `юг`→`{ЮАО,ЮВАО,ЮЗАО}`;
     `запад`→`{ЗАО,СЗАО,ЮЗАО}`; `восток`→`{ВАО,СВАО,ЮВАО}`.
   - Диагонали (точный округ): `юго-запад`→`{ЮЗАО}`, `юго-восток`→`{ЮВАО}`,
     `северо-запад`→`{СЗАО}`, `северо-восток`→`{СВАО}`.
   - Гейт как в текущем `resolve_area`: если во фразе есть слово-не-направление
     («Северное Бутово») — НЕ кардинал, идём дальше.
2. **Разговорная зона** (`named_zones` по `name`/`aliases`, регистронезависимо) →
   `ST_DWithin(geom::geography, точка::geography, radius_m)`.
3. **Имя района/округа** (`listings.raion`/`okrug` или `admin_zones` по `name`/`aliases`)
   → `raion = %s` / `okrug = %s` (по предвычисленной колонке, быстро).
4. **Кольцо** (`садовое`/`ттк`/`мкад`/`за мкад`) → `ST_Within(<ring>)` или окружная
   логика (за МКАД = `okrug = ANY('{ЗелАО,НАО,ТАО}')`).
5. **Nominatim-fallback** для произвольных топонимов: `polygon_geojson=1` — если вернулся
   admin-полигон, использовать его (`ST_Within`); если точка (кафе/ЖК/место) — радиус по
   типу/рангу (метро ~1.2км, ЖК ~300м, место ~3км).
6. Ничего не совпало → `None` (гео-фильтр не применяется, остаётся семантика).

### Авто-расширение (строго → шире)

Область — жёсткий фильтр. Расширение — отдельный слой в оркестраторе ПОСЛЕ штатной
relaxation-петли (которая ослабляет цену/минуты/окна). Если результатов всё ещё
`< min_results`, применяем следующий шаг `ZoneMatch.widen` и помечаем в `relaxed`:
- район → его округ → снять область;
- сторона света (набор округов) → снять область;
- named-зона (радиус R) → R×2 → снять область.
Каждый шаг добавляет запись в `relaxed` (например, «в самих Хамовниках вариантов мало —
расширил до ЦАО»), которая доезжает до объяснения выдачи.

### NLU

Поле `ParsedQuery.area: str | None` уже есть (коммит c45530f). NLU извлекает фразу
области; всю раскладку делает резолвер. Обновить промпт примерами: «в Хамовниках»→
area="Хамовники", «в центре»→area="центр", «у Патриков»→area="Патрики», «внутри
Садового»→area="внутри Садового". Кросс-язык: «northern Moscow»→area="север".

## Границы модулей

- `habitus/geo/zones.py` (новый) — импорт `admin_zones`/`named_zones` из GeoJSON/сида,
  backfill `listings.okrug/raion`.
- `habitus/online/geo.py` — `resolve_area` расширяется до слоёной цепочки (кардинал-map
  в коде; запросы к `admin_zones`/`named_zones`/`listings`-колонкам через conn).
- `habitus/online/orchestrator.py` — авто-расширение области.
- `habitus/db/schema.sql` — таблицы `admin_zones`/`named_zones`, колонки `okrug`/`raion`.
- `habitus/cli.py` — `import-zones`.
- `habitus/online/nlu.py` — примеры промпта.

## Тестирование

- `resolve_area` (юниты, без сети): кардинал→SQL по округам; центр→ЦАО; диагональ→округ;
  гейт «Северное Бутово»→дальше; named-alias→`ST_DWithin`; имя района→колонка; fallback.
- `import-zones` (фикстура-GeoJSON): `admin_zones` наполнена, `listings.okrug/raion`
  проставлены через `ST_Contains`.
- PostGIS-интеграция: объекты в известных округах → «север»/«центр»/«Хамовники»
  фильтруют корректно.
- Оркестратор: авто-расширение область при <min_results, пометка в `relaxed`.
- Не гонять на наполненной dev-БД (TRUNCATE) — отдельная `habitus_test`.

## Явно вне охвата (YAGNI)

H3/geohash; изохроны/«время до работы»; обучение моделей; ТТК как отдельная зона (только
Садовое + ЦАО + за-МКАД в v1, ТТК — при желании позже); UI-выбор зоны на карте (это
зона фронта/беков, здесь только NL-резолвер).

## Открытый пункт реализации

Точный способ получения GeoJSON округов/районов из OSM (osm-boundaries.com ручной
экспорт vs build-скрипт Overpass+PostGIS-сборка полигонов) — решается в плане
реализации; на дизайн не влияет, т.к. `import-zones` читает готовый GeoJSON-файл.
