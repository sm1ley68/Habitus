# Обогащение выдачи из уже собранных данных + city-скоуп

**Дата:** 2026-08-14
**Статус:** дизайн (спека)

## Проблема

Три симптома с общей причиной: данные, которые уже собраны и лежат на диске, до
пользователя не доезжают.

1. **Выдача — десять неотличимых карточек** «2-комн, 54 м²». `display_fields.go`
   синтезирует имя из площади и комнат, `ObjectPassport.Address` — пустая строка с
   комментарием «no address text anywhere in the pipeline yet». При этом в
   `listings.csv` колонка `address` заполнена на 1000/1000, а `cian_loader.parse_csv`
   сознательно берёт 12 полей из 16 и выбрасывает `address`, `url`, `zhk`,
   `metro`, `building_material`, `deadline`.

2. **`walk_min_metro` считается по прямой** — расстояние до ближайшей точки OSM,
   делённое на 1.33 м/с. В том же CSV лежат маршрутные времена от Циана с именами
   станций и типом передвижения (1000/1000).

3. **Три тумблера слоёв карты всегда пустые.** `geo_layers_service.layerKinds`
   покрывает только POI-слои; `communal`, `noise` и `ecology` возвращают пустой
   `FeatureCollection`. При этом в `urban_evidence` лежит 55 302 записи по
   communal/crime/noise. Досье их читает, карта — нет.

Плюс два дефекта, вскрытых при разборе:

4. **В `poi` 173 школы на всю Москву** — на порядок меньше реального.
   `OVERPASS_QUERIES["school"]` запрашивает только `node`, тогда как школьные здания
   в OSM — это `way`. Для парков ту же проблему уже починили (`node; way; relation;`),
   для школ — нет. `walk_min_school` — заглавный сценарий продукта («школа в 10 минутах
   пешком») и одна из осей proximity-rerank.

5. **Слои `urban_evidence` — модельные прокси, а подаются как измерения.** Источники:
   `osm-start-date-communal-proxy` (по году постройки зданий),
   `poi-alcohol-density-crime-proxy` (по плотности алкомаркетов),
   `osm-traffic-noise-proxy` (по типам дорог, 46 335 LINESTRING вдоль улиц). При этом
   комментарий в `schema.sql` обещает «noise adapters supply an observed dB value»,
   досье показывает `crime_index` и `db` без указания происхождения, а `BuildTags`
   печатает «шум: low» как установленный факт. Это единственное место, где проект
   отходит от собственного правила «не выдумывать факты о городе».

## Цель

Довести московскую выдачу до состояния, когда каждое показанное число имеет источник и
подпись, — и сделать это так, чтобы следующий город (Дубай) не потребовал переделки уже
написанного. Обучения моделей нет, новых внешних источников нет: всё нужное уже лежит в
`listings.csv`, `urban_evidence` и OSM.

## Решения (утверждены на брейншторминге)

- **Гибридная схема (вариант C).** Явные колонки — для полей, участвующих в фильтрации,
  ранжировании или общем для всех городов UI. `source_extra jsonb` — для специфики
  источника. Граница проходит по вопросу «участвует ли поле в контракте между городами».
- **Метро: Циан в приоритете, OSM — фолбэк**, провенанс сохраняется отдельной колонкой.
- **`city` вводится сейчас, вместе со скоупом в запросах.** Самого Дубая не делаем —
  только измерение.
- **Слои:** оживить `communal` и `noise`, `ecology` заменить на `crime` (данные есть,
  под экологию источника нет нигде), школы дособрать.
- **`enrich` переписать на KNN** — раз всё равно пересчитываем после досбора школ.
- **`doc_text` получает адрес**, полный переэмбеддинг принят как разовая цена.
- **НЕ делаем в этой спеке:** регулярный парсинг и актуализацию, картинки квартир, сам
  Дубай, чат-бота по объекту (уже работает end-to-end). Каждое — отдельная спека.

## Архитектура

Изменение проходит вертикально через все три слоя, но нигде не меняет форму
взаимодействия: `city` течёт тем же путём, что уже течёт `point`, новые поля едут теми
же контрактами, что `price`/`area`/`rooms`.

```
listings.csv ──► cian_loader ──► raw_listings ──► promote_to_listings ──► listings
                 (16 полей,                        (city, address,          │
                  не 12)                            metro_station,          │
                                                    walk_min_metro_src)     │
                                                                            ▼
OSM Overpass ──► poi (school: node+way+relation, city) ──► enrich (KNN, city-scoped)
                                                                            │
                                                                            ▼
                                            doc_text (+адрес) ──► embed_pending
```

### Данные

Миграция — идемпотентными `ALTER`, тем же приёмом, что уже применён для
`okrug`/`raion` в `habitus/db/schema.sql`:

```sql
ALTER TABLE listings ADD COLUMN IF NOT EXISTS city               text NOT NULL DEFAULT 'msk';
ALTER TABLE listings ADD COLUMN IF NOT EXISTS address            text;
ALTER TABLE listings ADD COLUMN IF NOT EXISTS source_url         text;
ALTER TABLE listings ADD COLUMN IF NOT EXISTS metro_station      text;
ALTER TABLE listings ADD COLUMN IF NOT EXISTS walk_min_metro_src real;
ALTER TABLE listings ADD COLUMN IF NOT EXISTS source_extra       jsonb NOT NULL DEFAULT '{}';
CREATE INDEX IF NOT EXISTS listings_city_ix ON listings (city);

ALTER TABLE poi ADD COLUMN IF NOT EXISTS city text NOT NULL DEFAULT 'msk';
CREATE INDEX IF NOT EXISTS poi_city_kind_ix ON poi (city, kind);

ALTER TABLE raw_listings ADD COLUMN IF NOT EXISTS city         text NOT NULL DEFAULT 'msk';
ALTER TABLE raw_listings ADD COLUMN IF NOT EXISTS address      text;
ALTER TABLE raw_listings ADD COLUMN IF NOT EXISTS source_url   text;
ALTER TABLE raw_listings ADD COLUMN IF NOT EXISTS source_extra jsonb NOT NULL DEFAULT '{}';
```

`DEFAULT 'msk'` делает backfill существующих 979 строк бесплатным и корректным: всё, что
уже в базе, — московское.

**Почему `walk_min_metro_src` отдельно от `walk_min_metro`.** Источник пишет только в
`_src`, `enrich` вычисляет своё, итог собирается как `COALESCE(_src, вычисленное)`. Так
приоритет Циана реализуется без потери провенанса: по наличию `_src` всегда видно, откуда
взялось число. Это то же правило, по которому в `urban_evidence` уже разведены `weight`
и `db`. Перезаписать источник вычисленным значением означало бы потерять возможность
ответить на вопрос «откуда 7 минут».

**Что попадает в `source_extra`.** `zhk`, `building_material`, `deadline`, полный массив
станций метро с временами и типами передвижения. Это поля, специфичные для Циана: у
Bayut/Property Finder на их месте будут `community`, `developer`, `handover_date`. Они
уедут в тот же JSONB без миграции схемы, а общий контракт — город, адрес, цена, метро —
останется типизированным и индексируемым.

### Оффлайн-пайплайн

**Загрузчик.** `cian_loader.parse_csv` перестаёт выбрасывать поля. `address` и `url` →
свои колонки. Колонка `metro` — это JSON-массив вида
`[{"name":"Ленинский проспект","time":7,"transport_type":"walk"}, …]`; из него берётся
минимум по записям с `transport_type == "walk"` → `walk_min_metro_src`, имя этой станции
→ `metro_station`, весь массив → `source_extra`. Записи с `transport_type == "transport"`
игнорируются: это время на автобусе, а колонка называется `walk_min`. Новых зависимостей
нет — обычный `json.loads` над колонкой CSV. Битый или пустой JSON не роняет строку:
поле остаётся `NULL`, объявление грузится, дальше работает OSM-фолбэк.

`kaggle_loader` не трогаем: у него этих полей нет, и `source_extra` остаётся пустым
объектом по умолчанию.

**Где происходит вывод производных полей.** `raw_listings` остаётся зеркалом источника:
туда едут только `city`, `address`, `source_url` и нетронутый `source_extra`. Колонок
`metro_station` и `walk_min_metro_src` в сыром слое нет — их выводит
`promote_to_listings`, читая массив станций из `source_extra`. Так разбор формата
конкретного источника остаётся в одном месте, а сырой слой не приходится мигрировать
каждый раз, когда меняется способ вывода.

**Школы.** В `OVERPASS_QUERIES` запрос школ приводится к форме, уже работающей для
парков:

```python
"school": f'(node["amenity"="school"]{MSK_AREA};'
          f'way["amenity"="school"]{MSK_AREA};'
          f'relation["amenity"="school"]{MSK_AREA};);',
```

Bbox запроса остаётся московским: города в Overpass-слое эта спека не параметризует,
потому что второго города ещё нет. Колонка `poi.city` заполняется константой при
загрузке — она нужна, чтобы `enrich` и слои уже сейчас скоупились корректно.

`parse_overpass` менять не нужно — он уже берёт `el["center"]` для way/relation.
Ожидаемый порядок после пересбора: ~1500 школ вместо 173.

**`enrich` на KNN.** Текущий `_ENRICH_SQL` считает `MIN(ST_Distance(...))` по всем POI
данного вида без `ST_DWithin` — GIST-индекс не используется, сложность равна
`|listings| × |poi|`. После досбора школ множитель вырастет на порядок. Переписывается на
`LATERAL` с оператором `<->`:

```sql
walk_min_school = (
  SELECT MIN(ST_Distance(l.geom::geography, p.geom::geography)) / 1.33 / 60.0
  FROM (SELECT geom FROM poi
        WHERE kind = 'school' AND city = l.city
        ORDER BY geom <-> l.geom LIMIT 5) p
)
```

Пять кандидатов, а не один, потому что `<->` упорядочивает по планарному расстоянию в
градусах, а планарно ближайший объект на широте Москвы не всегда геодезически ближайший;
на пяти кандидатах расхождение исчезает. Итоговое расстояние по-прежнему считается через
`geography`, то есть значения остаются сопоставимыми с прежними.

`bar_density_500m` остаётся счётчиком через `ST_DWithin` — он и сейчас индексируется
нормально. Во все подзапросы добавляется `AND p.city = l.city`.

Метро отдельной строкой: `walk_min_metro = COALESCE(l.walk_min_metro_src, <KNN>)`.

**`doc_text` и переэмбеддинг.** `build_doc_text` получает адрес и станцию метро. Это
меняет `content_hash` у всех строк, поэтому `embed_pending` пересчитает эмбеддинги
целиком — единожды, порядка минут на CPU. Базовую линию eval после этого надо переснять:
и адрес в тексте, и новые значения `walk_min_school` сдвинут и recall/NDCG, и
proximity-ось. Это ожидаемо и должно быть зафиксировано как новая точка отсчёта, а не
воспринято как регрессия.

### Контракт: ML → Go → фронт

**Город — параметр запроса, не поле разбора.** `city` не кладётся в `ParsedQuery`:
пользователь его не произносит, он приходит из чата. Течёт тем же путём, что уже течёт
`point`: `SearchRequest.city` → `run_search` → `retrieve_with_relaxation` →
`hybrid_search` → `build_where` (клауза `city = %s`). `resolve_area` тоже получает город:
сейчас в нём зашито `f"{area}, Москва"` для Nominatim, а таблица `CARDINAL` знает только
московские округа. Для другого города таблица округов просто не совпадёт и резолв уйдёт в
геокодер — деградация, а не ошибка.

**Адрес попадает в промпт объяснения — осознанно.** Сейчас `GROUNDED_SYSTEM` прямо
запрещает называть адреса, районы и станции метро, потому что их не было в блоке ФАКТЫ.
Как только `address` и `metro_station` появляются в `address_facts`, запрет с этих двух
полей снимается: объяснение сможет сказать «три варианта в Хамовниках, до Парка культуры
7 минут» вместо обезличенного текста, оставаясь grounded. Остальная часть запрета —
названия школ, ЖК, произвольная география — сохраняется дословно.

**Go.** `domain.Listing` и `listing_repo` дочитывают `address` и `metro_station` — та же
выборка, которая уже читается ради `price`/`area`/`rooms`/`level`. `SynthName` становится
фолбэком на случай отсутствующего адреса, а не единственным путём. `ObjectPassport.Address`
перестаёт быть честной заглушкой. `ml_client.SearchRequest` получает `City`, который
`search_stream_service` берёт из `chat.City`; `object_service.go`, где сейчас захардкожен
`City: "msk"`, начинает брать оттуда же.

**Слои так отдать нельзя.** В сыром виде `crime` — это ~4 МБ GeoJSON (4466 полигонов по
33 точки), `noise` — 8–12 МБ (46 335 линий). Поэтому:

- `GET /geo/layers` получает параметр `bbox` вида `minLon,minLat,maxLon,maxLat` в
  EPSG:4326 — тот же порядок `[lng, lat]`, что и везде в проекте. Для evidence-слоёв он
  обязателен, для POI-слоёв игнорируется;
- геометрия отдаётся через `ST_SimplifyPreserveTopology` с допуском `0.0001` (~10 м на
  широте Москвы) — тот же порядок величины, что уже используется для границ зон в
  `area_geojson`;
- предел — 5000 фич на слой; при срезе ответ несёт `truncated: true` по этому слою;
- фронт запрашивает evidence-слой под текущий вьюпорт и перезапрашивает при
  существенном сдвиге камеры.

POI-слои (школы, бары, парки, метро) остаются как есть — они мелкие и грузятся целиком.

**Фронт.** В `LayerId` `ecology` меняется на `crime`, добавляется `metro`. `Property`
получает `address`, `PropertyCard` показывает его вместо синтезированного имени.
Переключатель города чистит `layerData` и `properties` и двигает камеру — сейчас
`useMaplibre` читает `city` один раз при монтировании и на смену не реагирует.

Заодно чинится расхождение типов: `price_from`, `rooms`, `area_sqm` объявлены в
`types.ts` как `number`, но Go шлёт указатели и присылает `null` — `money(null)` сейчас
молча рисует «0 млн ₽».

### Честность прокси-слоёв

Ни один из трёх слоёв не является замером, поэтому ни один не подписывается как замер.

- Комментарий в `schema.sql` про «observed dB value» приводится в соответствие с
  реальностью: это модельное значение, а не наблюдение.
- Каждый evidence-слой несёт происхождение в `properties` фичи и в легенде карты:
  «модель по типам дорог», «плотность алкомаркетов», «по году постройки зданий».
- В досье блоки `social_environment` и `view_and_climate` получают строку источника
  рядом со значением — в тот же `verdict_line`, где уже живёт «Риски рассчитаны только по
  точным импортированным слоям».
- `BuildTags` перестаёт печатать «шум: low» как факт. Пока `noise_level` выводится из
  плотности баров, тег называет то, что действительно измерено: «баров рядом: 0».
- `noise_level` получает недостающую градацию `medium`. Сейчас `enrich` даёт только
  `high` (более двух баров в 200 м) и `low`, тогда как `ParsedQuery.noise_max`,
  `build_where` и фронт про `medium` знают — ветка мёртвая. Порог берётся из
  `urban_evidence` слоя noise: модельное значение дБ в радиусе 500 м даёт три градации
  вместо двух, а барный прокси остаётся фолбэком там, где покрытия нет.

### match_score

`RescaleScoreFromStored` пересчитывает уже сблендированный score без ранга и без
`degraded`, из-за чего карточка в списке и открытый паспорт показывают разные проценты.
Исправляется в источнике: посчитанный `match_score` сохраняется в `chat_search_results`
рядом со `score` и читается обратно, вместо повторного вычисления из другого контекста.

## Обработка ошибок и деградация

Принцип прежний: отсутствующий слой деградирует, а не роняет запрос.

- Битый/пустой `metro` JSON в CSV → `walk_min_metro_src` остаётся `NULL`, работает
  OSM-фолбэк. Объявление грузится.
- Пустой `address` → `SynthName` как сегодня.
- Overpass недоступен при пересборе школ → в `poi` остаются прежние строки, `enrich`
  считает по ним; это уже покрыто существующим ретраем с backoff.
- `bbox` не передан для evidence-слоя → слой возвращается пустым с явной причиной, а не
  500-й ошибкой; тумблер помечается как сегодня («нет данных»).
- Превышен предел числа фич → отдаём срез с `truncated: true`, фронт показывает, что слой
  показан частично.

## Тестирование

Существующие тесты остаются валидными: `city` везде получает `DEFAULT 'msk'`, поэтому
текущие фикстуры продолжают работать без правок.

Новое:

- `cian_loader`: разбор `metro` JSON — выбор минимума среди `walk`, игнор `transport`,
  устойчивость к битому JSON и пустой строке; попадание `zhk`/`building_material` в
  `source_extra`.
- `promote_to_listings`: `address`, `source_url`, `metro_station`, `walk_min_metro_src`
  доезжают до `listings`; идемпотентность повторного прогона сохраняется.
- `enrich`: приоритет `COALESCE(_src, KNN)` — объявление с источником не перезаписывается
  вычисленным значением, объявление без источника получает вычисленное;
  city-скоуп — POI чужого города не участвует; эквивалентность KNN-переписи прежнему
  результату на фикстуре.
- `osm_extract`: запрос школ содержит way и relation; `parse_overpass` берёт `center`.
- `build_where`: клауза города присутствует и параметризована.
- `build_doc_text`: адрес и станция попадают в текст.
- `geo_layers_service`: evidence-слой без `bbox` пуст; с `bbox` фильтрует; предел числа
  фич выставляет `truncated`; `ecology` больше не в списке, `crime` и `metro` — в нём.
- Фронт: `LayerId` покрывает новый набор; `money(null)` не рисует «0 млн ₽»; смена города
  сбрасывает слои и объекты.
- Go: `match_score` из списка равен `match_score` в паспорте для одного объекта.

## Порядок работ

Порядок продиктован зависимостями по данным: каждый следующий шаг читает результат
предыдущего.

1. Миграция схемы (колонки + индексы, backfill через `DEFAULT`).
2. Загрузчик и `promote_to_listings`, повторный прогон `listings.csv`.
3. Пересбор POI со School-фиксом.
4. Перепись `enrich` на KNN + city-скоуп, полный пересчёт.
5. `doc_text` + полный переэмбеддинг, пересъём базовой линии eval.
6. Контракт ML → Go (city, address, промпт объяснения).
7. Слои: evidence-источник, `bbox`, лимит, подписи происхождения.
8. Фронт: `LayerId`, адрес в карточке, переключатель города, nullability.
9. Честность: `medium` для шума, подписи источников, `match_score`.

Шаги 1–5 меняют данные и должны идти строго последовательно. Шаги 6–9 независимы между
собой и могут выполняться параллельно.

## Риски

- **Пересъём eval.** Шаги 3–5 меняют и признаки, и текст документов. Метрики сдвинутся;
  без явной фиксации новой точки отсчёта это будет выглядеть как регрессия. Снять
  базовую линию до шага 3 и после шага 5.
- **Объём evidence-слоёв.** Даже с `bbox` и упрощением слой шума на плотном центре может
  оказаться тяжёлым. Предел числа фич обязателен, а не желателен.
- **Время пересбора Overpass.** Запрос школ с way/relation тяжелее нынешнего; публичный
  Overpass отдаёт транзиентные 429/504. Ретрай уже есть, но шаг 3 надо закладывать
  минутами, а не секундами.

## Дальше (отдельными спеками)

- Регулярная актуализация: приём от Go-парсера каждые ~15 минут, инкрементальный досчёт
  гео и эмбеддингов, деактивация ушедших объявлений. Упирается в готовность парсера,
  который живёт вне этого репозитория и отработал разово.
- Картинки квартир: схема, сбор по `source_url`, хранение/проксирование, отдача.
  `source_url` из этой спеки — необходимое условие.
- Дубай: второй источник данных, город в `CARDINAL`/`admin_zones`, локализация. Схема к
  этому моменту уже готова.
