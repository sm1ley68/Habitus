# Личный кабинет продавца + импорт объявления с Циана

**Дата:** 2026-08-23
**Статус:** дизайн (спека)

## Проблема

Habitus сегодня — рабочее пространство покупателя. Аутентификация в нём уже есть
и работает: `users`, `sessions`, HttpOnly-кука `habitus_session`,
`middleware.Auth` на всех ручках кроме `register`/`login`, и `AuthGate`
(`frontend/components/auth/AuthGate.tsx`) закрывает вообще весь фронт. Чего нет —
**кабинета**: ни профиля, ни «моих объявлений», ни выхода из аккаунта
(`logout()` объявлен в `frontend/lib/api/auth.ts:38` и не вызывается нигде),
аватар в левом рейле — статичная буква «Г» с `aria-hidden`
(`frontend/components/shell/LeftRail.tsx:66`).

Поэтому у продавца квартиры в системе нет никакой работы, которую он мог бы
выполнить. Его Core Job — «я хочу, чтобы мою квартиру увидели подходящие
покупатели». Витрина уже умеет объяснять объект лучше Циана (досье, гео-факты,
чат по объекту), но попасть в неё продавец не может: единственный путь данных —
батч-обход Циана раз в сутки.

Второе: объявления в базу попадают только через `scripts/refresh.sh` →
`cmd/cian-parser` → `listings.csv` → `habitus offline`. Продавец, чью квартиру
краулер уже собрал, видит свой объект в чужой витрине и не может им управлять.

## Цель

Дать продавцу кабинет, в котором он за одну-две минуты доводит квартиру до
состояния «опубликована в Habitus и находится поиском» — либо вставив ссылку на
своё объявление с Циана, либо заполнив карточку с нуля. Плюс закрыть очевидную
дыру: если объявление уже есть в нашей базе, сказать об этом и отдать объект под
управление продавцу, а не упереться в «дубликат».

Вне объёма этой итерации: роли и права, админ-консоль модерации, аналитика
просмотров, платные размещения, чат покупателя с продавцом, второй источник
(Авито).

## Решения, зафиксированные до дизайна

Четыре развилки закрыты явным выбором:

1. **Импортированное объявление попадает в общий поиск** наравне со
   спарсенными — индексируется BGE-M3, обогащается гео-фактами, находится
   поиском и видно на карте. Кабинет, чьи объявления не видит витрина, не
   выполняет работу продавца.
2. **Совпадение по `cian_<id>` — это привязка, а не отказ.** Объявление,
   которое краулер уже собрал, переходит под управление продавца.
3. **Владение объявлением не проверяется** (ни SMS, ни модерация). Объект несёт
   `verification = unverified`, публикуется автоматически, у оператора есть
   рубильник `OWNER_AUTOPUBLISH` и возможность снять объявление. Осознанный
   риск MVP: любой может «забрать» чужую квартиру.
4. **В объём входит и создание с нуля**, а не только импорт — значит нужна
   загрузка фотографий, которой в проекте нет вообще.

## Архитектура

Ключевое ограничение — **граница владения БД**. Go владеет своими миграциями
(`backend/migrations/`), Python владеет `listings`, `raw_listings`, `poi`,
`urban_evidence` и остальной витриной (`habitus/db/schema.sql`), Go читает их
только на чтение (`backend/internal/db/migrate.go:14-16`,
`backend/internal/repository/listing_repo.go:1-3`).

Второе ограничение — **эмбеддинги считает Python**. BGE-M3 живёт в
`habitus/embed/encode.py`; объект, записанный в `listings` в обход Python,
останется без `embedding`/`sparse_embedding`, и семантический поиск его не
найдёт. Объявление, которое лежит в базе и не находится, хуже отсутствующего.

Отсюда разделение:

- **Go — система учёта продавца.** Таблица `owner_listings`: владение, статусы,
  черновики, правки, ссылки на фото. Всё, что продавец видит и меняет.
- **Python — витрина.** Две новые ручки принимают опубликованное объявление,
  валидируют, кладут в `listings`, точечно обогащают и индексируют.
  **`raw_listings` не трогаем**: эта таблица — зеркало обхода источника, а
  объявление продавца ни в каком снимке не участвует.
- Go зовёт Python при публикации и снятии через существующий
  `internal/client/ml_client.go`.

Рассмотренные и отклонённые альтернативы:

- **Go пишет в `listings` напрямую.** Отклонено: объект без вектора не
  находится (см. выше), плюс ломается граница владения схемой.
- **Отложенная публикация пачкой из `scripts/refresh.sh`.** Отклонено: задержка
  до часа между «опубликовал» и «нашлось». Момент, когда продавец видит свою
  квартиру в системе, — единственный Aha Moment этой фичи; откладывать его
  нельзя.

## Данные

### Go: миграция `0010_owner_listings`

```sql
CREATE TABLE owner_listings (
    id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id      uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    external_id  text NOT NULL UNIQUE,
    origin       text NOT NULL CHECK (origin IN ('cian','manual')),
    status       text NOT NULL DEFAULT 'draft'
                 CHECK (status IN ('draft','publishing','published','unpublished','failed')),
    verification text NOT NULL DEFAULT 'unverified'
                 CHECK (verification IN ('unverified','verified')),
    city         text NOT NULL CHECK (city IN ('spb','msk')),

    price        bigint,
    area         real,
    kitchen_area real,
    rooms        integer,
    level        integer,
    levels       integer,
    address      text,
    lng          double precision,
    lat          double precision,
    window_orientation text[],
    description  text,
    photos       text[] NOT NULL DEFAULT '{}',

    source_url   text,
    import_error text,

    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    published_at timestamptz
);

CREATE INDEX owner_listings_user_ix ON owner_listings (user_id, updated_at DESC);
```

`external_id UNIQUE` — это и есть механизм «объявление привязано к другому
аккаунту»: конфликт вставки разрешает гонку двух одновременных импортов одной
ссылки без блокировок и без проверки-перед-вставкой.

Формат `external_id`:

- импорт с Циана — `cian_<id>`, тот же, что кладёт `habitus/ingest/cian_loader.py:70`.
  Совпадение с уже собранной строкой `listings` даёт привязку бесплатно;
- создание вручную — `owner_<uuid4-без-дефисов>`.

`source` в `listings`: у импортированного остаётся `'cian'` (id стабилен, дедуп
работает естественно), у созданного вручную — `'owner'`.

`photos` — массив URL, а не файлов: у импортированного это ссылки на CDN Циана
(`https://images.cdn-cian.ru/...`), у созданного вручную — наши
`/static/uploads/<listing_id>/<uuid>.<ext>`. Фото Циана **не перекачиваем**.

### Python: `habitus/db/schema.sql`

Одна идемпотентная колонка, в стиле остальных ALTER'ов файла:

```sql
ALTER TABLE listings ADD COLUMN IF NOT EXISTS owner_managed boolean NOT NULL DEFAULT false;
```

Она закрывает две коллизии с батч-пайплайном:

1. **Краулер гасит объявление продавца.** `deactivate_missing`
   (`habitus/update/incremental.py:84`) гасит по скоупу `source`. Продавец,
   снявший объявление с Циана, но оставивший его у нас, потерял бы его на
   следующем обходе. Условие выборки получает `AND NOT owner_managed`.

2. **Краулер перетирает правки продавца.** `promote_to_listings`
   (`habitus/clean/normalize.py:38`) делает `ON CONFLICT (external_id) DO UPDATE`
   по всем колонкам. Если объявление всё ещё висит на Циане, следующий обход
   вернёт старую цену поверх новой. `DO UPDATE` получает
   `WHERE NOT listings.owner_managed`.

Обе правки — сужение существующих запросов, ничего не переписывается.

### Валидация координат по городам

`is_valid` (`habitus/clean/normalize.py:9`) жёстко зашита на `MSK_BBOX`. Для
объявления продавца в Петербурге это отказ без объяснения. Вводится:

```python
CITY_BBOX = {
    "msk": (37.30, 55.48, 37.95, 55.95),
    "spb": (29.60, 59.70, 30.70, 60.20),
}
```

`MSK_BBOX` остаётся как алиас `CITY_BBOX["msk"]` — вызовы из батч-пайплайна не
меняются; проверка получает город параметром с дефолтом `"msk"`.

## Импорт с Циана

### Извлечение id

Принимаются формы: `cian.ru/sale/flat/<id>/`, `/rent/flat/<id>/`,
`/deal/sale/flat/<id>/`, поддомены (`m.cian.ru`, `spb.cian.ru`), любые
query-хвосты (`?mlSearchSessionGuid=...` Циан навешивает всегда), и голый
числовой id. Всё остальное — `cian_url_invalid` с человеческим текстом, а не
`validation_error` «invalid request body».

### Порядок проверок — в Циан идём последними

1. **`owner_listings` по `external_id`.** Свой → 200 с вердиктом
   `already_yours` и id карточки. Чужой → 409 `listing_claimed_by_other`.
2. **`listings` по `external_id`.** Краулер уже собрал объект → вердикт
   `claimable`, данные для предпросмотра берутся **из нашей базы**, похода в
   Циан нет вообще. С учётом того, что база — половина Москвы, это будет
   основной путь: мгновенный и не создающий риска бана.
3. **Запрос в Циан** — только если объекта нет нигде.

### Забор одного объявления

`BuildSearchBody` (`backend/internal/cian/client.go:201`) сейчас собирает
`jsonQuery` из региона, комнат, цены и страницы. Добавляется ветка поиска по id:

```go
query["ids"] = map[string]any{"type": "terms", "value": []int64{offerID}}
```

и метод `Session.FetchByID(ctx, offerID) (*Listing, error)` поверх той же
`session.do` + `ParseSearchResponse`. Пустой результат → `ErrOfferNotFound`.
Модель `cian.Listing` (`backend/internal/cian/model.go:14`) уже содержит всё
нужное карточке: цена, площадь, комнаты, этаж и этажность, адрес, метро, фото,
ЖК, материал, координаты, URL.

### Защита от бана

Батч-режим (`cmd/cian-parser`: паузы 3–6 с, обход страниц, ротация прокси) для
интерактивного импорта не годится, поэтому импорт получает свой слой:

- **пул сессий и прокси** из `CIAN_PROXIES` — механика уже есть в
  `backend/internal/cian/pool.go`, переиспользуется как есть;
- **глобальный token bucket** на исходящие запросы к Циану, по умолчанию 6 в
  минуту (`CIAN_FETCH_PER_MIN`). Это верхняя граница, не зависящая от числа
  пользователей: сколько бы человек ни импортировали одновременно, наружу уходит
  не больше;
- **per-user лимит** импортов в час (`OWNER_IMPORT_PER_HOUR`, по умолчанию 20) —
  по образцу `backend/internal/http/middleware/ratelimit.go`, с инъекцией
  `now func() time.Time` для тестов без `time.Sleep`;
- `cian.ErrBlocked` и превышение bucket'а → **не 500**, а `cian_unavailable` с
  текстом «Циан сейчас не отдаёт данные. Попробуйте позже или заполните карточку
  вручную» и переходом в ручную форму, предзаполненную ссылкой.

Прокси в проде обязательны: `cmd/cian-parser/main.go:114` отказывается работать
без них не случайно, а после реального бана
(`docs/notes/cian-blocked-2026-08-17.md`).

### Нечёткий дубль

После получения данных (любым из трёх путей) — поиск похожего объекта:

```sql
SELECT external_id, address, price, area FROM listings
WHERE is_active
  AND rooms IS NOT DISTINCT FROM $rooms
  AND level IS NOT DISTINCT FROM $level
  AND abs(area - $area) <= 1.0
  AND ST_DWithin(geom::geography, ST_MakePoint($lng,$lat)::geography, 150)
  AND external_id <> $external_id
LIMIT 3;
```

Результат — **предупреждение, не блокировка**: одна и та же квартира,
перевыставленная под новым id Циана, встречается регулярно, и решать, дубль это
или нет, должен продавец. Вердикт `similar_found` + список найденных объектов.

## Публикация

Новые ручки Python-сервиса (`habitus/online/service.py`, по образцу
существующих `@app.post("/dossier")`):

```
POST /listings/owner-upsert   OwnerListingUpsertRequest  → OwnerListingUpsertResponse
POST /listings/owner-withdraw {external_id}              → {external_id, deactivated}
```

Схемы — в `habitus/online/schema.py`, единственный источник правды по формам
данных. `OwnerListingUpsertRequest` повторяет поля `owner_listings` плюс
`external_id`, `source`, `city`.

Шаги `owner-upsert`:

1. **Валидация.** Цена 1 млн — 3 млрд, площадь 5–1000 м², координаты внутри
   bbox своего города — те же пороги, что у батч-пайплайна (`is_valid`),
   переиспользуются, а не дублируются. Провал → 422 с указанием поля.
2. **`INSERT … ON CONFLICT (external_id) DO UPDATE`** в `listings`:
   `owner_managed = true`, `is_active = true`, `geom` через
   `ST_SetSRID(ST_MakePoint(lng,lat),4326)`.
3. **Точечное обогащение.** `_ENRICH_SQL` (`habitus/geo/enrich.py:68`) уже
   параметризован фильтром `%(filter_geog)s`; добавляется второй фильтр
   `%(filter_ids)s::text[]` (`AND (%(filter_ids)s::text[] IS NULL OR
   l.external_id = ANY(%(filter_ids)s))`) и обёртка `enrich_ids(conn, ids)`.
   Существующие `enrich_all` и `enrich_around` передают `None` и не меняются.
4. **`doc_text` и эмбеддинг.** `build_doc_text` (`habitus/embed/document.py:8`)
   для строки, затем `embed_pending` — он инкрементален по `content_hash` и
   подхватит только изменившуюся запись.
5. Ответ `{external_id, indexed: true}`.

Таймаут в Go — `ML_OWNER_TIMEOUT_S` (по умолчанию 60): шаг с эмбеддингом
занимает секунды, а на холодной модели — заметно дольше.

Статусная машина в кабинете: `draft` → `publishing` → `published`. Ошибка ML →
`failed` с текстом в `import_error` и кнопкой «Повторить». Снятие с публикации →
`owner-withdraw` → `is_active = false`; строка в `listings` остаётся, при
повторной публикации оживает.

Досье объекта (`GET /objects/{id}`), карта и чат по объекту заработают на
объявлении продавца **без единой правки** — они читают `listings` и
`urban_evidence` по `external_id`.

## API шлюза

Все ручки за `authMw`, владение проверяется по образцу
`ChatService.GetOwned` (`backend/internal/service/chat_service.go:38`).

```
GET    /api/v1/owner/listings                  список продавца
POST   /api/v1/owner/listings/import/preview   {url} → предпросмотр + вердикт дедупа
POST   /api/v1/owner/listings/import           {url} → создать или привязать
POST   /api/v1/owner/listings                  создать вручную (черновик)
GET    /api/v1/owner/listings/:id
PATCH  /api/v1/owner/listings/:id              правка полей
POST   /api/v1/owner/listings/:id/publish
POST   /api/v1/owner/listings/:id/unpublish
DELETE /api/v1/owner/listings/:id
POST   /api/v1/owner/listings/:id/photos        multipart, до 20 файлов
DELETE /api/v1/owner/listings/:id/photos        {url} в теле
```

Фото идентифицируются URL, а не отдельным id: в `owner_listings.photos` лежит
упорядоченный `text[]`, и в нём смешаны ссылки CDN Циана и наши
`/static/uploads/...`. Отдельная таблица фотографий ради MVP не заводится, а
синтетический `photo_id` поверх массива был бы фикцией. Порядок фото меняется
`PATCH`'ем всего массива.

Продавец может доложить свои фотографии и к импортированному объявлению —
массив смешанный по происхождению, ограничение в 20 штук общее.

**Вердикт предпросмотра** — `new`, `claimable` или `already_yours`; это три
взаимоисключающих состояния самого объявления. Похожие объекты — **отдельное
поле** `similar: [{external_id, address, price, area}]`, ортогональное вердикту:
новое объявление вполне может иметь похожего соседа. Пустой массив — обычное
дело, не ошибка.

Формат ошибок — существующий конверт
`{"error":{"code","message"}}` (`backend/internal/http/middleware/errorenvelope.go:24`).
Новые коды в `internal/apperr`: `cian_url_invalid`, `cian_offer_not_found`,
`cian_unavailable`, `listing_claimed_by_other`, `owner_listing_not_found`,
`photo_too_large`, `photo_unsupported_format`, `photo_limit_exceeded`.

### Фотографии

Внешнее хранилище не нужно: `app.Static("/static", cfg.StaticDir)` уже поднят
(`backend/internal/app/app.go:65`).

- путь `<StaticDir>/uploads/<listing_id>/<uuid>.<ext>`, отдача — `/static/uploads/...`;
- **тип определяется по сигнатуре файла** (`http.DetectContentType`), а не по
  расширению и не по заголовку `Content-Type` клиента;
- допустимы `image/jpeg`, `image/png`, `image/webp`; ≤10 МБ на файл; ≤20 фото на
  объявление;
- имя файла клиента не используется в пути вообще — только сгенерированный UUID;
- удаление объявления удаляет каталог.

Ресайза нет: объём и разрешение ограничены на входе, а вводить обработку
изображений ради MVP не стоит.

## Фронтенд

Сейчас приложение — один роут `/` с переключением «экранов» полем zustand-стора
(`frontend/lib/store/session.ts:10`). Кабинету это не подходит: нужны диплинки,
кнопка «назад» и отдельный лэйаут. Поэтому — настоящие роуты Next, рабочее
пространство покупателя на `/` не трогаем:

```
/lk                    Мои объявления
/lk/import             импорт с Циана
/lk/new                мастер создания
/lk/listings/[id]      карточка: превью + правка
/lk/profile            профиль, выход
```

`AuthGate` поднимается в общий лэйаут (сейчас он внутри `app/page.tsx`), чтобы
покрывать оба дерева роутов. `logout()` получает наконец точку вызова, аватар в
`LeftRail.tsx:66` становится ссылкой в кабинет.

### Экраны

**Пустое состояние `/lk`** — не заглушка, а сразу главное действие: крупное поле
«Вставьте ссылку с Циана», под ним неприметная ссылка «или заполнить вручную».
Импорт — самый дешёвый для продавца путь, он и должен быть визуально главным.

**Список объявлений** — карточки со статусом, ценой, адресом и датой обновления.
**Никаких выдуманных метрик**: счётчиков просмотров и звонков в системе нет,
рисовать их нельзя (правило проекта — не выдумывать факты).

**Предпросмотр импорта** — три исхода, каждый со своим тоном:

| вердикт | что видит продавец |
|---|---|
| `new` | карточка с подтянутыми данными, кнопка «Импортировать» |
| `claimable` | «Мы уже знаем эту квартиру» + готовая карточка + «Это моя квартира» |
| `already_yours` | «Объявление уже в вашем кабинете» + переход на карточку |

Непустой `similar` рисуется поверх любого из них предупреждающей полосой со
ссылками на похожие объекты — кнопка действия при этом остаётся активной.

Отдельно — состояние `cian_unavailable`: объяснение и кнопка «Заполнить
вручную», ведущая в мастер с предзаполненной ссылкой.

**Мастер создания `/lk/new`** — четыре шага: точка на карте → параметры → фото →
цена и описание. Точка ставится пином на maplibre (уже подключён,
`frontend/lib/map/useMaplibre.ts`): это точнее и быстрее, чем геокодер, и снимает
зависимость от Nominatim. Адрес вводится строкой рядом. Черновик сохраняется
`PATCH`'ем на каждом шаге — уход со страницы не теряет работу.

**Карточка `/lk/listings/[id]`** — слева превью ровно в том виде, в каком объект
увидит покупатель, справа панель правки. Продавец видит следствие своей правки, а
не абстрактную форму.

**Профиль `/lk/profile`** — имя, email, выход из аккаунта.

### Примитивы UI

Дизайн-системы в проекте нет: `tailwind.config.ts` содержит один цветовой токен
`accent`, каталога `components/ui/` не существует, классы пишутся инлайном (в
`PropertyCard.tsx:27` один `className` длиной ~350 символов). Кабинет — пять
экранов, плотно состоящих из форм; писать их тем же способом значит гарантировать
кашу.

Поэтому в объём входит минимальный набор примитивов `frontend/components/ui/`:
`Button`, `Input`, `Select`, `Field` (лейбл + ошибка + подсказка), `Card`,
`Badge`, `Dialog`, `Toast`. Не абстрактный UI-кит, а ровно то, что нужно этим
экранам, на существующих CSS-токенах (`app/globals.css:21-36`). Библиотеки форм
не вводим: формы плоские, `useState` + валидация на сабмите достаточно.

Планка доступности задана существующим `frontend/components/a11y.test.tsx` и
глобальными `:focus-visible` / `prefers-reduced-motion` — новые экраны её держат:
у каждого поля лейбл, у каждой иконочной кнопки `aria-label`, ошибки связаны с
полями через `aria-describedby`.

## Риски

**Главный риск — доступность Циана, и он не в коде.** С машины разработки
`www.cian.ru` и `api.cian.ru` отдают 403 на обычный запрос (проверено), а в
`docs/notes/cian-blocked-2026-08-17.md` зафиксирована капча после ~2400
объявлений при ~11 запросах в минуту с домашнего IP. Поэтому этап 3 начинается с
дешёвого пробника: один реальный запрос по id через настроенный прокси. Если он
не проходит — путь `claimable` (объект уже в базе) и ручное создание работают
как ни в чём не бывало, а импорт деградирует в понятную ошибку с переходом в
ручную форму. Фича теряет удобство, но не проваливается целиком.

**Второй риск — «забрать» чужую квартиру.** Принят осознанно (решение 3).
Смягчение: `verification = unverified` в схеме с первого дня, `OWNER_AUTOPUBLISH`
как рубильник, снятие с публикации в один запрос. Настоящая проверка (код на
телефон из объявления) — отдельная задача, схема к ней готова.

**Третий риск — расхождение витрины и кабинета.** `owner_listings` в Go и
`listings` в Python — две записи одного объекта. Синхронизирует их только вызов
`owner-upsert` при публикации. Провал вызова оставляет статус `failed` — то есть
расхождение видно продавцу и лечится кнопкой «Повторить», а не молча копится.
